# Sincronización automática de ajustes

`Core` está integrado en el Host de Windows y coordina el transporte HTTPS firmado, cifrado de extremo a extremo, outbox/checkpoints DPAPI, cursor account-wide monotónico, proyección local, consentimiento, reintentos, resolución de conflictos y reset compartido. El cursor es independiente de la revisión del documento y se guarda con el outbox. Cuando no cambia, el runtime termina el ciclo sin bajar el ciphertext; los servidores anteriores que no exponen el endpoint siguen usando la lectura completa. La sincronización se activa solo con consentimiento explícito y cubre tema, idioma y duración predeterminada; reglas, perfiles, permisos, agenda, historial y enforcement siguen locales.

El estado actual está validado en suites locales (Sync151/151, Host241/241), con fallback 404→GET y edición concurrente durante el cursor cubiertos por pruebas del worker; además, hay dos sesiones Host sobre HTTPS loopback y dos runtimes contra el `ContentDocumentLedger` real sobre PostgreSQL efímero. La prueba Host también pasa una edición `preferences.set` por el `NativeBridgeDispatcher` y `HostAccountService` antes de llevar tema, idioma y duración al otro dispositivo; las preferencias locales permanecen intactas. Además, dos `HostSettingsSyncSession` consultan el cursor y convergen a través de las rutas HTTP `/v1/documents` reales en TestServer; esa subprueba usa bearer/userinfo sintéticos e issuer HTTPS. La ruta OIDC/API con Keycloak/JWT reales se valida aparte. La aceptación física automática en dos PCs y staging siguen pendientes.

Ejecutar desde la raíz del repositorio:

```powershell
dotnet test cloud/sync/Tests/FocusGuard.Sync.Tests.csproj -c Release
```

El adaptador verifica primero membresía, firma y descifrado FG-E2EE-1. El núcleo no autentica entradas. Usa snapshots verificados y rechaza conflictos antes de crear/cifrar una escritura CAS; un ACK solo cuenta como confirmación si coincide con operación, revisión y payload. El transporte conserva ID y bytes cifrados para reintentos. Nunca envía overrides, rutas de apps, permisos, enforcement, claves ni historial dentro del documento global.

`Windows` añade persistencia DPAPI de base/borrador/outbox y una actualización read-modify-write protegida por lease OS. Esperar su commit antes de enviar; conservar la operación preparada y sus bytes exactos en reintentos. Un ACK no debe borrar el borrador de una edición posterior. Corruptos, scopes distintos y temporales huérfanos requieren recuperación explícita.

`SettingsSyncLocalStorage.PrepareCurrentUserDirectory` prepara `%LocalAppData%\FocusGuard\Sync` y una carpeta por hash de issuer/cuenta/generación/dispositivo. Protege root y scope con DACL explícita (usuario actual, SYSTEM y Administrators), verifica el propietario y rechaza reparse points; los IDs no aparecen en la ruta. El Host usa esta ruta protegida para su estado de sincronización y conserva el vault de identidad separado.

SettingsEnvelopeCodec reutiliza FG-E2EE-1 para documentos normales de los tres ajustes; las pruebas adicionales usan primitivas reales y DPAPI, con identidades sintéticas. Las pruebas básicas de outbox aún usan bytes opacos para aislar su lógica. Las pruebas locales no representan convergencia física en dos PCs.

Una prueba local adicional ejecuta dos runtimes con vaults/consentimientos/checkpoints DPAPI separados, dos identidades firmantes y crypto FG-E2EE-1 real. Un servidor de prueba verifica firma y CAS y conserva solo el sobre cifrado; señales de cambio local/reconexión llevan ambos clientes a converger. Esto sigue siendo una simulación local y no aceptación física en dos PCs.

Windows incluye un worker caller-driven: valida consentimiento/scope, lee documentos, guarda la preparación durable antes de publicar y confirma mediante lectura criptográficamente verificada. El runtime y el Host lo invocan solo después del opt-in persistido. El proveedor de autores usa historia de membresía verificada y permisos `WriteSettings`; fixtures adicionales cubren historias sintéticas.

`SettingsSyncContextFactory` crea crypto solo desde el `RestoredDeviceMaterial` vinculado y una cadena completa de membresía. Un test DPAPI de dos revisiones verifica que un dispositivo recién unido pueda abrir un documento firmado por el autor histórico; con la cadena truncada se rechaza. `HostAccountService` conserva y valida `MembershipChain` tanto para transferencia como para la sesión de sincronización automática.

`SettingsDocumentHttpTransport` construye solicitudes firmadas y valida respuestas/ETag/cursor y errores; `NativeSettingsRequestSender` mantiene el bearer dentro del módulo de identidad existente. El test HTTPS loopback con certificado pinneado corre dos Host completos con sesiones, tokens y proofs de dispositivo separados sobre un ledger sintético. En el fixture local, 125 checks ejercitan rutas del API con OIDC/Keycloak; 15 cubren runtimes contra el ledger y cinco Host checks pasan por `/v1/sync/cursor` y `/v1/documents`. Se valida que un cursor sin cambios omita la descarga del documento, además de CAS, conflicto, resolución y tombstone. Estas pruebas no sustituyen la aceptación física ni staging.

`SettingsRetryController` añade una compuerta caller-driven con cooldown monotónico, backoff/jitter, respeto de Retry-After y parada ante errores críticos. El `SettingsRetryCheckpointStore` conserva bajo DPAPI/current-user el backoff de fallos transitorios con scope issuer/account/generation/device; al reiniciar, espera la duración completa desde un reloj monotónico nuevo, de forma conservadora. Un fallo de lectura/escritura/borrado se detiene como `NeedsAttention(Storage)`. Un checkpoint corrupto detiene la sincronización; `ResetAfterOwnerRecoveryAsync(ownerConfirmed: true)` elimina solo ese checkpoint y temporales huérfanos del store, después de que el usuario complete recuperación local deliberada. El Host ofrece esta recuperación de forma explícita.

`SettingsSyncScheduler` corre solo si Host restaura o guarda el consentimiento local. Hace una reconciliación al inicio y luego espera cooldown o señales agrupadas de cambio local, conectividad o consentimiento. Una señal puede adelantar un poll ocioso, pero respeta Retry-After, backoff, conflicto sin resolver y errores que requieren atención. `SettingsAutomaticSyncRuntime` compone consentimiento, cancelación y store durable. Tras persistir una resolución explícita, el Host usa `NotifyConflictResolved` para reintentar enseguida; una edición normal no salta el cooldown de conflicto ni Retry-After. Las señales de red despiertan únicamente una sesión consentida.

`SettingsConflictResolutionService` exige la revisión, máscara de campos y borrador exactos que se mostraron al usuario; rechaza diálogos obsoletos, aplica la elección solo a los campos en conflicto y conserva los otros campos locales. Rechaza conflictos de reset para no borrar tombstones. Persiste primero y avisa al runtime después.

`SettingsSyncDesktopTick` ejecuta el worker y, salvo `Disabled`, proyecta el outbox vigente a `DesktopSettingsSyncStore` bajo el lease del vault. La proyección copia tema, idioma y duración y conserva todas las preferencias locales; bytes idénticos no se reemplazan repetidamente. Un error local se informa como `NeedsAttention(Storage)`. El Host crea este tick bajo consentimiento y emite señales después del commit local.

`SettingsAutomaticSyncCoordinator` enruta cambios de los tres ajustes: `EditAsync` y `EditSelectedAsync` terminan el commit del outbox/proyección antes de avisar `NotifyLocalSettingsChanged`; `ReapplyAsync` solo repara la proyección y no dispara red. Con consentimiento apagado el borrador permanece local y el runtime no ejecuta el tick.

El reset local preparado usa una intención Deleted y un tombstone cifrado/firmado; requiere confirmación, no un flag de servidor ni ausencia HTTP. Outbox/ACK conservan la distinción entre borrado y defaults normales; cambios offline previos o reset concurrente quedan bloqueados por conflicto.

`SettingsExport` prepara un JSON portátil de los tres ajustes con versión, selección y preview/confirmación. No exporta IDs, credenciales, permisos ni estado de outbox y no aplica o publica por sí mismo. El Host exige confirmación nativa antes de compartir o importar.

`DesktopSettingsProjection` adapta los tres campos al `DesktopSettings` real. Conserva permisos/enforcement, perfiles, accesibilidad y las demás preferencias locales; aplica overrides únicamente a la proyección local y el Host lo usa bajo el lease de preferencias.
