# FG-103 Native messaging host

## Continuation plan: real service handoff

1. Define one bounded, versioned health-only contract for extension heartbeat/status
   requests and authoritative service-health responses.
2. Add a cancellable named-pipe client in the native host and a single-request
   named-pipe listener in the Windows Service, with explicit connect/I/O timeouts.
3. Reject unknown, malformed, oversized, over-nested, mismatched, activation, and
   release messages before they reach service state.
4. Keep session state read-only on this route; the service may report health and
   session status but cannot activate or release a session for the extension.
5. Cover disconnect, timeout, invalid-message, cancellation, and service-restart
   behavior with automated tests.
6. Publish the validated service build, update the already-installed development
   service in place, and run a host-to-service health/restart drill without browser
   registration.
7. Run formatting, Release build, focused tests, and the full validation suite;
   then update `TASKS.md` and this checkpoint.

### Continuation acceptance criteria

- Native and pipe payloads are bounded, strictly shaped JSON with a maximum depth,
  protocol version, message type, non-empty correlation ID, and UTC timestamp.
- The host uses finite connect and I/O timeouts and propagates caller cancellation.
- A disconnected, stopped, timed-out, or restarted service yields an explicit
  degraded result; no request can silently activate or release a session.
- The service is the only producer of service/session health and returns a fresh
  service-instance ID after restart.
- Tests demonstrate disconnect, timeout, malformed/unsupported input, correlation
  validation, cancellation, and reconnect after listener restart.
- The installed-service drill records the exact service identity, pipe response,
  stop/disconnect observation, restart response, and rollback/recovery command.

### Continuation security, UX, and recovery implications

- Security: the pipe accepts only the health contract, enforces local Windows pipe
  access plus bounded framing, and never exposes activation or release operations.
- UX: no browser or desktop registration changes occur; health can be called
  connected only when the service response is current and validated.
- Recovery: stopping/restarting the development service makes the host fail
  degraded and reconnect on the next request. The existing uninstall script
  remains the rollback for the installed development service.

## Plan

1. Add a dedicated native messaging executable with bounded Chromium framing.
2. Validate the browser-supplied launch origin against an exact extension-origin allowlist.
3. Keep the service handoff behind an interface and fail closed until a real transport is supplied.
4. Generate Chrome and Edge host manifests into repository-local staging only.
5. Provide and test an idempotent staging rollback before any browser registration.
6. Run formatting, build, .NET tests, extension tests, and a manifest/rollback smoke drill.

## Acceptance criteria

- Frames use a four-byte little-endian length prefix and reject empty, oversized,
  truncated, malformed, or over-nested JSON.
- Output is bounded by the same explicit size limit.
- Only exact canonical `chrome-extension://<id>/` origins present in the host manifest
  are accepted; malformed origins, HTTP origins, and prefix matches are rejected.
- The executable does not contact the service for a rejected origin.
- Chrome and Edge manifests contain an absolute host path and explicit
  `allowed_origins`.
- Preparation does not write browser registry keys or browser policy.
- Rollback removes only the repository-local native-host staging directory and is
  safe to repeat.

## Security implications

The browser process is not trusted merely because it can start the executable.
Origin validation is exact and derived from the staged manifest. Frame lengths,
JSON depth, and message count are bounded before dispatch. The initial handler
exposes health only and does not activate, alter, or release policy.

## UX implications

There is no new end-user UI in this slice. Browser health cannot be claimed as
connected until registration and service handoff are separately verified.

## Recovery and rollback

No Chrome, Edge, registry, policy, service, or machine ACL state is changed.
`scripts/remove-native-messaging-staging.ps1` removes only
`artifacts/FocusGuard.NativeMessaging` after resolving and validating that exact
repository-local path. Re-running rollback is a no-op.
