# FG-110 task log

## Plan and acceptance criteria

1. Define a deterministic immutable policy delivery and SHA-256 identity shared
   by the service, process monitor, native host, and extension.
2. Add an explicit receiver contract. The process monitor stores only a valid,
   unexpired snapshot and returns its policy ID and hash; the browser exchanges
   its previous acknowledgement for the current snapshot through the bounded
   native-messaging heartbeat.
3. Keep the authoritative session in `Activating`/degraded state until the
   process and browser acknowledgements both exactly match the current policy.
   `EnforcementConnected` is true only while both matches remain current.
4. Clear delivered policy automatically at expiration and never invoke process
   termination or browser request blocking in this milestone.
5. Cover matching acknowledgements, stale policy/hash, unavailable components,
   reconnection, and automatic expiration in automated tests.
6. Run formatting, Release build, all .NET tests, extension tests, and update
   the graph, task queue, and this checkpoint with the evidence.

Acceptance requires both consumers to acknowledge the same immutable policy ID
and SHA-256 hash before connected health is reported; missing, stale, or failed
acknowledgements must be visibly degraded; expiration must withdraw the policy
without the Desktop; and no real blocking path may be activated.

## Security, UX, and recovery implications

- The hash covers a deterministic, versioned policy representation; policy ID,
  session ID, timestamps, strictness, ordered rules, and rule values are bound.
- All browser messages remain versioned, shape-checked, bounded, local, and free
  of browsing history. A stale acknowledgement cannot confirm a newer policy.
- A component failure is fail-open for this distribution-only milestone and is
  reported as degraded rather than falsely connected.
- The service remains authoritative for finite expiration. On expiry it removes
  the distributable snapshot and consumers clear their local copy on the next
  exchange/evaluation; strict recovery semantics are unchanged.
- The Desktop already exposes `EnforcementConnected`; it will now become true
  only from verified acknowledgements and false again on degradation/expiry.

## Summary

The authoritative service now creates a versioned immutable `PolicyDelivery`
with a unique policy ID and deterministic SHA-256 hash. It distributes that
delivery to the process-monitor receiver immediately and exposes it to the
browser extension through the existing bounded native-messaging heartbeat.

Each consumer returns the exact policy ID and hash. The session remains
`Activating` and reports degraded enforcement until the process acknowledgement,
browser acknowledgement, and fresh extension heartbeat all agree. It then
transitions idempotently to `Active`; stale IDs/hashes or a component failure
cannot set `EnforcementConnected`. Expiration withdraws the delivery and clears
consumer state without invoking any blocking behavior.

## UX implications

The existing active-session health surface now receives truthful state:
`Activating`/degraded while acknowledgements are incomplete, connected only
after both consumers confirm the same snapshot, and disconnected again if the
extension heartbeat becomes stale. No new UI strings or screens were required.

## Security implications

The SHA-256 identity binds the schema, policy ID, session/profile IDs, UTC
window, strict flag, and ordered application/website rules. Both .NET and the
extension independently recompute integrity. Native messages remain strict,
bounded to the same 64 KiB activation ceiling, and reject partial ID/hash pairs.

This milestone deliberately fails open: receivers only store policy and never
call process termination or browser blocking APIs. A stale acknowledgement is
discarded rather than treated as partial success.

## Recovery implications

Finite expiration remains service-authoritative for both `Activating` and
`Active` sessions. Expired process policy is cleared locally; the next browser
exchange receives no policy and clears browser storage. Existing strict
persistence and delayed elevated recovery are unchanged.

## Limitations

- Policy delivery is pull-based for the MV3 extension and therefore becomes
  connected on its next heartbeat, not synchronously in the Desktop request.
- The process monitor receiver holds and validates the snapshot but does not yet
  feed it to process termination.
- The extension holds and validates website rules but does not yet register
  blocking listeners.
- This workspace has no `.git` directory, so SCM diff/status was unavailable.
