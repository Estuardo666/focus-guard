## Summary

Implemented the strict-persistence engine as a service-owned, finite,
integrity-checked policy snapshot. It atomically saves and recovers immutable
strict policy, expires without the desktop UI, quarantines corrupt state
fail-open, and reconciles clock movement using UTC plus monotonic elapsed time.

The Windows service hosts the persistence worker, but it remains inactive unless
a DPAPI `LocalMachine`-protected integrity key has been provisioned. FG-105 did
not provision that key or arm a policy. Production strict activation remains
closed until FG-106 supplies and tests the required recovery flow.

## UX implications

There is no new UI or broader product claim. The desktop continues to identify
strict behavior as simulated. Exact expiration and recovery warnings must remain
visible when real activation is connected later.

## Security implications

- Snapshots are bounded to 1 MiB and 10,000 rules and validated before use.
- HMAC comparison is constant-time; key bytes are cleared after worker use.
- The integrity key is expected only as a DPAPI `LocalMachine` blob and is not
  stored with the snapshot.
- Invalid or corrupt state fails open and is quarantined when possible.
- Clock rollback cannot extend a session within a boot; persisted trusted UTC
  clamps rollback across service restarts.
- No process, browser, registry, network, account, ACL, recovery-tool, or
  security-tool enforcement was performed.

## Limitations

- FG-105 implements persistence but does not make strict mode shippable.
- DPAPI key provisioning, recovery-code validation, delayed elevated recovery,
  and the activation handshake remain FG-106.
- A real armed strict-policy reboot was not repeated because FG-104 already
  proved reboot/expiration and arming without recovery would violate the gate.
- HMAC protects integrity only after secure key provisioning and ACLs.
