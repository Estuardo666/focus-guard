## Summary

Implemented an independent elevated recovery utility and service-authoritative
delayed release. Recovery codes use 160 bits of entropy; only a salted
PBKDF2-SHA256 hash is persisted. A valid code creates an atomic,
HMAC-authenticated request, and the service releases only after the finite delay.

## UX implications

The utility clearly displays the exact local eligibility time and explains that
it may be closed because the service owns the delay. It never echoes the code.
Desktop activation is still not connected; when connected it must show the code
once and require saved-code acknowledgement.

## Security implications

- No code is accepted through process arguments.
- No plain code is persisted or included in audit.
- Wrong and tampered requests cannot cause release.
- The utility requires an existing administrator token and does not automate UAC.
- The recovery executable is protected from application termination rules.
- The drill used an empty policy and performed no enforcement.

## Limitations

- Desktop strict activation still needs to connect code generation and saved-code
  acknowledgement to the service activation transaction.
- Production installation, utility staging, uninstall behavior, and final
  production ACL layout belong to FG-107.
- The development drill used a one-minute delay; automated tests prove the
  production default is exactly 15 minutes.
