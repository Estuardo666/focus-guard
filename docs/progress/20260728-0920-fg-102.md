# FG-102 checkpoint

## Plan

1. Convert `FocusGuard.Service` into an executable Generic Host that supports the Windows Service lifetime.
2. Keep the development service explicitly non-enforcing: no process termination, IPC listener, persistence, ACL changes, registry edits, or session activation.
3. Add a cancellable background worker with injected `TimeProvider` and observable lifecycle state for automated tests.
4. Add reviewable PowerShell install, status, and uninstall scripts with exact service name/path checks and idempotent rollback.
5. Build and test before any Service Control Manager mutation.
6. Install only from an already elevated owner-run shell, start the service, verify running/stopped behavior, then leave or remove it according to the documented procedure.

## Acceptance criteria

- Release service executable builds with zero warnings.
- Console/debug lifetime starts and stops cleanly in an automated test.
- Windows Service hosting is enabled only when launched by SCM.
- Development service performs no enforcement and cannot activate sessions.
- Installation is manual, owner-present, explicit, and limited to `FocusGuard.Development`.
- Status and rollback commands verify the exact service.
- Full automated suite passes.
- FG-102 remains incomplete until SCM reports the installed service running and rollback is demonstrated.

## Security implications

Installing a Windows Service creates persistent machine state and normally starts code outside the interactive user session. The development host therefore contains no process controller reference, accepts no IPC, loads no arbitrary code, stores no secrets, and performs no blocking. The service name and binary path are constants in the scripts. No elevation is attempted from the application or scripts.

## UX implications

There is no new desktop claim or control. The current UI must continue to say `Service simulator connected` until authenticated IPC and real health reporting exist.

## Recovery and rollback

The uninstall script stops `FocusGuard.Development`, waits for `Stopped`, deletes only that exact SCM entry, and verifies removal. If start fails, collect `sc.exe query` output and uninstall; do not widen permissions, change ACLs, or run as LocalSystem merely to make the test pass.

## Environment prerequisite

The current Codex process is not elevated (`IsAdministrator=False`). It may build and test the host but must not attempt SCM installation. The owner must explicitly execute the install command from an elevated PowerShell window.

## Summary

Implemented the non-enforcing FG-102 development service host and reviewable SCM scripts. No enforcement, IPC, storage, policy activation, elevation, or machine ACL behavior was added.

## First installation attempt

The owner ran the elevated install script. SCM created `FocusGuard.Development` and set its description, but `Start-Service` failed. Read-only diagnostics showed:

- Service state: `Stopped`
- Account: `NT AUTHORITY\LocalService`
- Start mode: manual
- SCM event: System log, Service Control Manager event 7000
- Error: `Access is denied`
- Process ID: 0; the service executable never started

Root cause: the configured executable was under the interactive user's private profile. `LocalService` could not traverse that path, so the failure occurred before FocusGuard code ran.

The fix preserves the least-privileged account. The install script now stages the Release output under `%ProgramData%\FocusGuard\Development\Service` and registers that exact executable. It does not modify ACLs or switch to `LocalSystem`. The uninstall script validates the staging path before recursively removing only that development-service directory.

All updated scripts pass PowerShell parser validation. The failed SCM entry must be removed with the updated uninstall script before reinstalling.

## Second installation attempt

The updated script successfully staged files and registered the service at:

`C:\ProgramData\FocusGuard\Development\Service\FocusGuard.Service.exe`

The inherited directory and file ACLs grant built-in Users read/execute access, and SCM launched the process. The service then crashed before connecting to SCM:

- SCM events 7009 and 7000: 30-second connection timeout.
- .NET Runtime event 1026: unhandled `FileNotFoundException` for `System.ServiceProcess.ServiceController, Version=10.0.0.0`.
- Application Error event 1000 confirmed the staged executable started.

The DLL was present, had the correct assembly identity, matched the source hash, and was readable. The root cause was deploying the generic `net10.0` build output, whose dependency graph contains both generic and Windows runtime assets without a fixed deployment RID.

The service is now published framework-dependent for `win-x64`. Its `.deps.json` selects `runtimes/win/lib/net10.0/System.ServiceProcess.ServiceController.dll`, and the publish includes the Windows-specific EventLog companion assembly. The install script now accepts only this RID-specific publish directory. A non-elevated `publish-development-service.ps1` script makes the prerequisite repeatable and refuses elevated builds.
