# FG-111 task log

## Plan and acceptance criteria

1. Add an explicit enforcement opt-in to the versioned activation contract and
   surface it in Desktop with finite-session consequences and recovery copy.
2. Gate confirmed-policy use on exact process and browser acknowledgements; any
   missing/stale acknowledgement, component failure, invalid hash, or expiration
   must withdraw effective enforcement and report a precise degraded reason.
3. Connect `ProcessMonitorPolicyReceiver` to the existing matcher and Windows
   process action boundary, preserving allow precedence, protected exclusions,
   graceful close, grace period, termination, and process-instance deduplication.
4. Connect the extension's stored confirmed policy to navigation listeners. It
   must allow browser-internal URLs, degraded/expired policy, and invalid hashes,
   and must never persist or transmit query strings, fragments, or history.
5. Add service, Desktop, monitor, native-messaging, and extension tests for
   acknowledgement gating, failures/reconnections, matching, precedence,
   deduplication, protected processes, integrity, and expiration.
6. Run format, Release build, all .NET and extension tests, manual owner-present
   validation, rollback verification, and `graphify update .` before closing.

Acceptance requires applications and sites to be blocked only when enforcement
was explicitly enabled and both consumers acknowledge the same intact FG-110
snapshot. Expiration releases both paths automatically; partial component loss
is fail-open and visibly degraded; recovery and protected exclusions remain
available; all quality gates pass.

## Security, UX, and recovery implications

- Security: enforcement never consumes a Desktop draft or an unacknowledged
  delivery. Integrity, freshness, protected-process exclusions, and allow-over-
  block precedence are checked at the last responsible enforcement boundary.
- Privacy: browser evaluation is local; only the sanitized origin/path needed
  for a matched audit event may be retained, and query/fragment data and browsing
  history never cross native messaging.
- UX: the opt-in is separate from strict mode. Status explicitly distinguishes
  `Activating`, `Connected`, `Degraded`, and `Expired`, including a reason and
  the exact finite end time.
- Recovery: expiration, normal stop, and elevated delayed recovery remain
  service-authoritative and withdraw policy. Failure of either consumer releases
  both enforcement paths instead of leaving a partial block.

## Owner-present scope and rollback

The owner explicitly authorized FG-111 and this Codex process is elevated. Safe
automated tests precede any manual real-blocking check. The manual target is only
the repository's `FocusGuard.TestTarget.exe`; no security/recovery/system process
is eligible. Rollback is: stop the finite normal test session, verify the policy
receiver and extension storage are cleared, stop the development service if it
was started for the drill, and use the existing installer rollback procedure if
any deployed binary was replaced. No registry, browser force-install policy,
ACL, account, credential, boot, firewall, or recovery setting will be weakened.

## Summary

FG-111 binds a default-off `EnforcementEnabled` opt-in into the FG-110 policy
hash. The process receiver exposes policy only after both exact acknowledgements;
the 500 ms service worker then matches immutable rules, preserves protected
exclusions, requests graceful close, waits two seconds, terminates if necessary,
and deduplicates by PID/start time. Expiration or degradation releases it.

The MV3 extension evaluates top-level navigation from the confirmed stored
snapshot. It redirects blocked matches to its local status page and fails open
for internal URLs, invalid hashes, expired windows, degraded health, and disabled
enforcement. Desktop adds the separate opt-in and explicit `Activating`,
`Connected`, `Degraded`, and `Expired` explanations.

## UX implications

Enforcement is visibly default-off and independent of strict mode. `Activating`
never claims blocking; degradation explains that both paths are released; expiry
states automatic release. The new checkbox has an accessible name and uses the
existing semantic-token surface.

## Security implications

The opt-in bit is integrity-bound. Pending, stale, expired, corrupt, or partially
acknowledged policy cannot reach either enforcement path. Protected FocusGuard,
Windows logon, security-health, disk-recovery, Task Manager, Registry Editor, and
accessibility processes remain excluded. Browser history, queries, fragments,
and navigation events never cross native messaging.

The broad non-protected controller mode is registered only inside the service
and receives targets from the confirmed immutable matcher. The standalone
developer controller remains disabled/allowlisted by default and its negative
owner-present checks pass.

## Recovery implications

Expiration, normal stop, and delayed elevated recovery remain service-owned and
withdraw policy. The final native drill observed an inactive service with no
delivery. The installer failure was recovered by gracefully closing only the
FocusGuard Desktop file holder, retrying transactionally, and verifying service
and production native-host health afterward.

## Limitations

Polling permits a brief launch window. Hash matching reads accessible files only.
Browser enforcement requires an installed/enabled MV3 extension and fails open
on loss. FocusGuard does not resist a determined administrator, Safe Mode,
offline edits, another OS, or recompilation.
