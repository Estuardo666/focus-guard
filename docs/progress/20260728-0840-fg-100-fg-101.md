# FG-100 + FG-101 checkpoint

## Plan

1. Review the owner-present termination design against the specifications, threat model, ADRs, and existing process simulator.
2. Add a harmless `FocusGuard.TestTarget` console executable with cooperative shutdown and bounded lifetime support.
3. Define explicit application-layer termination targets, options, statuses, audit events, and controller interfaces.
4. Add a fake controller and a Windows adapter guarded by default-off configuration, canonical path allowlisting, protected-process exclusions, and process-instance identity checks.
5. Add unit tests for allowed and rejected targets, protected processes, disabled operation, cancellation, timeout/access failures through fakes, auditing, and architecture boundaries.
6. Document the owner-present integration procedure without launching or terminating a real process.
7. Run formatting, Release build, and all automated tests; update `TASKS.md` only where acceptance evidence supports completion.

## Acceptance criteria

- FG-100 has a documented, reviewable design with security, UX, recovery, and rollback implications.
- `FocusGuard.TestTarget` builds and is harmless by construction.
- Real process termination is disabled by default and restricted to an exact canonical executable path.
- Protected or unauthorized targets cannot reach a termination primitive.
- Results are explicit and auditable without exposing executable paths in ordinary audit messages.
- Unit tests do not terminate real processes.
- FG-101 remains incomplete until the owner-present integration test demonstrates real detection and termination.

## Security implications

The slice introduces a future destructive capability but keeps it unreachable unless an explicit development option and exact executable path are supplied. The adapter must reject protected names, path mismatches, ambiguous process identity, and disabled configuration before requesting termination. No elevation, persistence, service installation, process injection, or arbitrary process-name termination is permitted.

## UX implications

The desktop remains configuration/status-only and receives no direct dependency on `System.Diagnostics.Process`. User-visible results must distinguish disabled, rejected, already-exited, access-denied, cancelled, and failed outcomes; no success claim is allowed before confirmation.

## Recovery and rollback

Real termination stays disabled by default. Removing the opt-in configuration or the Windows adapter registration removes the capability. The owner-present test targets only the dedicated disposable executable; if the test misbehaves, it can be closed normally with Ctrl+C or from Task Manager. FocusGuard recovery and Windows security tools remain protected.

## Summary

FG-100 is complete. The design keeps orchestration in `FocusGuard.Application`, all `System.Diagnostics.Process` access in `FocusGuard.Infrastructure.Windows`, and the desktop free of process APIs. FG-101 now has a safe, reviewable implementation and remains in progress because no real process was launched or terminated in this unattended cycle.

`FocusGuard.TestTarget` is a cooperative console application that reports its PID, emits a heartbeat, handles Ctrl+C, accepts `--mode cooperative`, and supports a bounded `--lifetime` from 1 to 3600 seconds.

The Windows controller is default-off and rejects requests before process discovery unless the executable is the dedicated test target at an exact canonical allowlisted path. It rejects protected names, ambiguous targets, and stale PID/start-time identities. It requests graceful close, waits for an injected timeout, forces only the verified instance when necessary, confirms exit, and converts expected platform failures into explicit results.

## UX implications

No desktop controls or claims were added. The result model can later present disabled, unauthorized, protected, missing, already-exited, access-denied, cancelled, failed, and confirmed-terminated outcomes without leaking generic exceptions.

## Security implications

There is no production configuration binding or service registration, so the real adapter is not reachable from the application today. Even when constructed explicitly, it requires both the development opt-in and the exact test-target path. Process identity is carried as PID plus UTC start time to mitigate PID reuse. The audit record excludes executable paths and arbitrary exception text.

## Limitations

- A console process generally has no closeable main window, so the current graceful request may return false and the verified test target may require forced termination after the grace period. Ctrl+C remains cooperative for manual recovery.
- The protected-process catalog is an initial minimum and must grow before general application blocking.
- No durable audit sink, service orchestration, UI surface, or production configuration loader is included.
- The owner-present integration evidence required by FG-101 has not been collected.
