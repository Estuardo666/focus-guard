## Hipótesis probada y límites

Se probó si el rechazo del cliente remoto puede completar o romper el accept loop del listener. La prueba crea un pipe GUID aislado con la misma primitiva nativa de producción (`PIPE_REJECT_REMOTE_CLIENTS`, ACL que deniega Network SID), inicia `FocusControlPipeService`, intenta conectar por `localhost`, confirma el rechazo Win32 error 5, luego hace una consulta local de status y cierra el listener normalmente. El rechazo no completa ni detiene el listener en este escenario.

La prueba debilita la hipótesis de que el rechazo remoto por sí solo explica el 7034, pero no reproduce la cuenta LocalService ni el ciclo de instalación observado. El código de `FocusControlPipeService.ExecuteAsync` sólo absorbe cancelación de shutdown en el límite externo y captura `IOException` alrededor de `WaitForConnectionAsync`; otra excepción de accept/setup podría escapar como fallo de `BackgroundService`. Es un camino candidato, no una causa confirmada. El host .NET usa `StopHost` como comportamiento predeterminado para excepciones no controladas de `BackgroundService` ([documentación de Microsoft](https://learn.microsoft.com/en-us/dotnet/api/microsoft.extensions.hosting.backgroundserviceexceptionbehavior?view=net-10.0)). El logging del servicio está limpiado en `Program.cs`, así que el SCM por sí solo no identifica la excepción. Para los 7034 del 6 de octubre tampoco hay evento .NET/WER correlacionado; no hay evidencia suficiente para atribuirlos a este camino. La hipótesis principal para la siguiente comprobación es ahora el ciclo de parada/sustitución del instalador, por la proximidad del último 7034 con la escritura del binario .79; hace falta correlación con transcript antes de cambiar el listener o el lifecycle.

## Traza de código del timeout compartido

- `FocusControlPipeService` configura un timeout por solicitud de5s. Cuando vence, `HandleClientAsync` captura `OperationCanceledException` si el token de parada del servicio no está cancelado, escribe `FocusControlPipeService.RequestTimeout` y después libera la capacidad; no relanza esa cancelación.
- `ExtensionHealthPipeService` configura3s y maneja igual el timeout de una conexión: registra `ExtensionHealthPipeService.RequestTimeout`, dispone el pipe y vuelve al bucle. Los fallos distintos de cancelación pueden escapar de la aceptación/creación del pipe, pero no hay un registro que pruebe que ese camino ocurrió.
- `ServiceFailureLog.WriteAsync` sólo guarda UTC, worker, tipo de excepción y HResult; no incluye stack trace. No hay una prueba que mencione directamente esos dos eventos `RequestTimeout` y no es posible reproducir el 7034 sin el contexto de instalación.
- Por tanto, las dos líneas a las12:24Z son timeouts no fatales de solicitudes, siete horas antes del 7034 local de las14:35 (19:35Z). No explican el 7034. La carpeta temporal `D:\TEMP\FocusGuard.Setup` no conserva logs y no existe `artifacts\fg235`; no apareció transcript para correlacionar la transacción del instalador. **Root cause: sigue sin determinar.** No se cambia el listener ni se atribuye causalidad.
