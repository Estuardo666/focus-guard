# FG-174 — Phase 5 native WebView2 host

Status: host slice implemented and locally validated. This checkpoint covers the parallel WinForms host only; it does not change the legacy Avalonia application, service, agents, installer, shared package versions, solution, or build scripts.

## Plan

1. Add `FocusGuard.Host.Windows` targeting `net10.0-windows`, using WinForms and the centrally managed Microsoft.Web.WebView2 package. Keep the standard Windows caption, `asInvoker`, PerMonitorV2, and user-local WebView2 data.
2. Package a local static shell and map only `focusguard.app` to its `ui` directory. Restrict top-level navigation and bridge sources to the exact local entry document; deny frames, popups, downloads, permissions, authentication prompts, certificate exceptions, and nonlocal resource requests.
3. Add a versioned typed status-read bridge with strict JSON shape, byte/depth bounds, source-origin and current-document checks, request deduplication/limits, and response projection. Compose it with a fail-closed Phase 4 authorization provider; do not issue pipe requests until an authorized native provider is installed.
4. Provide native runtime/setup/renderer failure UI and retry. Closing only releases the UI/document lifetime; it sends no session-stop command.
5. Add focused policy, schema, gate, mapping, flood, and document-lifetime tests. Build and run tests, then run a local host smoke with `--smoke` when WebView2 Runtime is present. The smoke gate must prevent any named-pipe service access.

## Security and recovery implications

- Phase 4's service-side process identity/role authorization is still absent from this checkpoint. The default provider reports `NotIntegrated`, and the bridge rejects even status reads before calling the real `NamedPipeFocusControlClient`. The page cannot set authorization readiness.
- The control bridge has no mutation method in this Phase 5 shell. `FocusGuard.Client` remains the only typed service transport; no mock transport is used in production composition.
- WebView2 content is local and offline. The host does not create a listener, start/stop the service, or stop a session on close/retry/renderer recovery.
- Runtime-missing and renderer recovery UI is implemented here. Installed package/runtime matrix, DPI hardware matrix, and service/agent/session continuity are not asserted until separately exercised.

## UX and security outcomes

- The host uses native WinForms caption, sizing, minimize/maximize and close controls. The manifest is `asInvoker`; the process also rejects elevated and non-medium-or-medium-plus integrity tokens. The normal WebView2 user-data directory is under `%LocalAppData%\FocusGuard\WebView2`.
- Runtime-not-found and generic startup errors show native text with Retry and Close. One automatic process-failure recovery is attempted before showing native retry UI. The local, runtime-missing, and simulated renderer-failure smoke paths each close within 20 seconds. Close, Retry, and renderer reload do not send stop or activation requests.
- Only `https://focusguard.app/index.html` can load as a document or send bridge messages. The host maps that virtual host to its packaged `ui` folder with cross-origin access denied. Nonlocal resource requests receive 403; frames, popups, downloads, permissions, authentication prompts, certificate exceptions, host objects, DevTools and context menus are denied/disabled. The static page also sets a restrictive CSP.
- The typed v1 bridge currently allowlists only `status.get`, with exact JSON members, 4 KiB request/8 KiB response bounds, depth and version checks, GUID request/document tokens, duplicate detection, a 60/minute limit, one in-flight status call, exact origin validation, and per-document cancellation. It maps only a bounded status projection from `FocusGuard.Client`.
- The default native authorization provider returns the typed `NotIntegrated` state. Thus even status reads stop before `NamedPipeFocusControlClient` is called; the bridge has no mutation method. A future Phase 4 provider can be composed natively, while JavaScript and settings cannot enable it.

## Limitations and next gate

This is not the completed Phase 5 gate and does not ship React, installer/package integration, a legacy-host fallback, tray/single-instance ownership, or service/agent/session lifecycle behavior. The actual Evergreen load and forced missing-runtime screen were exercised. Renderer recovery was exercised through the same native controller and WebView recreation path, but no actual renderer process was killed; DPI, caption/Snap, packaged-install, and broader Windows matrix flows remain untested. Do not claim full Phase 5 completion or installed enforcement continuity from this result. Keep the Phase 4 authorization unavailable until its identity/role/deployment proof is wired. Root should add the two project entries, run the combined solution validation, and update graphify after incorporating the new source files; shared solution, central props, build/installer files, and graph output were intentionally left to the root scope.
