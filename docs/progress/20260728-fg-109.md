# FG-109 checkpoint

## Plan and acceptance criteria

1. Extend SQLite profile storage with deterministic listing and deletion while
   preserving transactional rule replacement and validating every loaded row.
2. Connect Desktop profile selection and the Profiles navigation surface to the
   user-local SQLite store; create one honest empty starter profile only when the
   store is empty.
3. Send the selected profile's normalized application and website rules in the
   bounded activation IPC request.
4. Have the service validate and copy those rules into an immutable
   `EnforcementPolicy`; strict persistence must save that exact policy rather
   than an empty placeholder.
5. Keep `EnforcementConnected` false until an enforcement component has
   acknowledged the snapshot, and show that limitation plainly in the UI.
6. Add storage, contract, service, and Desktop tests, then run formatting,
   Release build, all .NET tests, extension tests, and relevant installer checks.
7. Verify the updated open application through its accessible desktop surface
   when the environment permits it.

Acceptance requires profile data to survive a Desktop restart, navigation and
selection to use real stored profiles, activation to reject malformed or
duplicate policy rules, post-activation profile edits to be unable to mutate the
service snapshot, strict persistence to contain the selected policy, and all
quality gates to pass with no warning or false enforcement claim.

## Security, UX, and recovery implications

- Policy crosses only the authenticated, versioned, size-bounded local control
  pipe and is revalidated by the authoritative service.
- The active policy is a defensive immutable copy; later SQLite edits cannot
  alter an active normal or strict session.
- Strict sessions remain finite and retain the existing one-time recovery-code
  and delayed elevated recovery behavior.
- No process termination, browser blocking, browser policy, registry, service
  identity, ACL, or recovery timing is changed by this milestone.
- Profiles and rule counts must no longer be labeled or populated as mock data.
  Degraded enforcement remains visible until real policy acknowledgement exists.

## Summary

Connected the Desktop profile selector to a user-local SQLite database and
removed the mock profile/rule counts. The first run creates one empty `Deep
Work` profile only when the database has no profiles. The Profiles navigation
control now opens and focuses the stored-profile selector.

Activation IPC now carries bounded application and website policy rules. The
service rejects malformed and duplicate rules, normalizes them into domain
records, and makes defensive read-only copies. Strict persistence stores that
exact policy instead of an empty placeholder. Enforcement health intentionally
remains false because process and browser components do not yet acknowledge
policy distribution.

## UX implications

The Focus screen exposes a keyboard-accessible stored-profile selector with real
application and website counts. The Profiles navigation button focuses and opens
that selector. Copy continues to state that the service has the immutable
snapshot while enforcement acknowledgements are still absent.

## Security and recovery implications

The activation boundary remains local, authenticated, versioned, shape-checked,
and limited to 64 KiB. Rule IDs must be unique across both families; action and
match enums are allow-listed; values are bounded; URL queries are rejected. The
service snapshot is independent of SQLite and caller-owned collections.

The production update ran only after all safe gates passed. The installer used
its existing binary/ACL/service rollback mechanism. No strict session was armed,
no recovery timing changed, and no process or website enforcement was enabled.

## Limitations

- Profile selection is connected, but full create/rename/duplicate/delete and
  integrated rule editing remain a later UI slice; the storage API supports
  save/list/load/delete transactionally.
- Process and browser policy consumers still do not acknowledge or enforce the
  snapshot, so `EnforcementConnected` remains false.
- Desktop accessibility inspection could not run because the `orca` executable
  is unavailable in this environment. Process/window-title verification and the
  owner's visible open application are the manual UI evidence.
- This workspace has no `.git` directory, so no diff or commit status was
  available.
