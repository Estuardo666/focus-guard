# FG-112 task log

## Plan and acceptance criteria

FG-112 is split into reviewable vertical slices. Each slice must pass its own
tests before the next one begins.

1. Establish a reproducible baseline and an automated E2E harness that drives
   Desktop's control client through the real service pipe, waits for exact dual
   acknowledgement, observes process and browser enforcement, and verifies
   expiration/release.
2. Exercise real disconnect/reconnect of the service, native host, and extension
   during an active finite session. Loss of either enforcement consumer must
   atomically withdraw both effective channels; reconnect may restore them only
   after fresh exact acknowledgements.
3. Validate restart reconciliation with active persisted enforcement, automatic
   expiration, corrupt-state fail-open, recovery, and an explicit rollback drill.
4. Persist sanitized application/browser audit events locally and expose a
   read-only, accessible Activity view without query strings, fragments, secrets,
   or unrelated browsing history.
5. Cache executable SHA-256 by stable file identity/metadata so the 500 ms poll
   does not reread unchanged binaries; invalidate conservatively and test changes.
6. Make the installer detect and gracefully close FocusGuard Desktop before DLL
   replacement, abort safely when it cannot close, and prove transactional
   rollback while Desktop was initially open.
7. Pin TypeScript as a development dependency, add the lockfile, run
   `tsc --noEmit` through the reproducible npm script, and enforce it in CI.
8. Add measured canaries for idle CPU, idle memory, process-detection latency,
   and 10,000-rule browser evaluation using the product budgets in `SPEC.md`.
9. Run formatting, Release build, all unit/integration/E2E tests, Chrome and Edge
   owner-present drills, restart/expiry/recovery/component-loss drills, installer
   update/rollback, performance canaries, and `graphify update .`.

Closure requires an explicitly opted-in finite session to block only the test
application and configured sites in real Chrome and Edge after both exact acks;
survive an ordinary reboot; fail open on expiration, recovery, corruption, or
component loss; retain only sanitized local audit records visible in Activity;
upgrade and roll back safely with Desktop initially open; and pass all quality
and performance gates.

## Security, UX, and recovery implications

- Security and privacy: the service remains authoritative. Every boundary uses
  validated bounded messages and integrity-bound immutable policy. Component
  loss is fail-open across both channels. Audit data is local, minimal, and
  sanitized before persistence; raw URL queries/fragments and secrets are never
  stored.
- UX: Activity must use resources and semantic tokens, remain keyboard/screen-
  reader accessible, and describe degraded/released states honestly. Locking
  actions retain exact expiration and recovery consequences.
- Recovery: all real drills use finite sessions and only the repository test
  target. Exact stop/cleanup/rollback commands and state checks are recorded
  before privileged mutation. No UAC/credential automation, ACL weakening,
  security-tool blocking, or broad process termination is permitted.

## Initial assessment

FG-111 already supplies opt-in gating, exact dual acknowledgement, 500 ms process
polling, extension navigation enforcement, persistence workers, and partial
disconnect tests. TypeScript configuration exists but the compiler is not pinned
or called by CI. The prior installer drill demonstrated the concrete open-Desktop
DLL replacement and rollback failure that FG-112 must correct. This directory has
no `.git` metadata, so change review will rely on explicit file inventories and
checkpoint records rather than repository diffs.
